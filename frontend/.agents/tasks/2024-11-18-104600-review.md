# Cafe POS and Billing System Implementation

Full-stack implementation of a role-based POS system with Angular frontend and Node.js/Express/MongoDB backend. The application enforces JWT authentication with admin and seller roles, restricting sellers to today's bills only (IST timezone) while giving admins full CRUD access to menu items, users, and historical sales data. The implementation follows a clean separation between backend controllers, middleware, and routes, with a standalone Angular architecture using functional guards and HTTP interceptors.

Watch for: None. The implementation is complete and correct across all critical paths.

**Verdict**: APPROVED

## High-level view

The backend enforces role separation at the middleware level using authMiddleware (JWT verification) followed by adminMiddleware (role check). Admin-only routes include user CRUD, menu write operations, and historical bills. Both roles can access menu GET (needed for billing) and bills POST. Sellers access today's bills via a separate endpoint that applies IST timezone filtering.

Bill creation snapshots menu item data (name, price) at time of purchase rather than storing references only, protecting historical bill integrity when menu prices change. The IST timezone logic correctly computes UTC boundaries by extracting the IST date, constructing UTC midnight, and subtracting the offset to find the corresponding IST midnight expressed in UTC.

The frontend uses Angular's functional guard pattern (CanActivateFn) and standalone components throughout. Both guards decode JWTs locally and check expiration before allowing access. The admin-guard redirects non-admins to the billing screen rather than login, which is correct UX. The token interceptor adds the Authorization header to all requests. All services use http://localhost:5000/api with correct HTTP methods. Component reactive forms include validators and display backend errors via MatSnackBar.

The billing screen implements cart logic with add/remove/quantity adjustment, calls the service to generate bills, and provides a print function that opens formatted receipt HTML in a new window. The getTodayBills endpoint restricts sellers to bills created on the current IST date only.

## Backend authentication and authorization flow

The authController login function performs bcrypt password comparison, checks the user's isActive status before issuing a token, and signs JWTs with an 8-hour expiration containing id, username, role, and name.

The authMiddleware extracts the token from the Authorization header using Bearer format, verifies it with jwt.verify, and attaches the decoded payload to req.user. The adminMiddleware checks `req.user.role !== 'admin'` and returns 403 if the check fails.

Routes compose middlewares in sequence: `router.get('/', authMiddleware, adminMiddleware, getAllUsers)`. Admin-only routes include all user operations, menu POST/PUT/DELETE, and bills GET. Both roles access menu GET, bills POST, and bills/today GET.

## Bill creation and item snapshot behavior

The billController createBill function validates the incoming items array, fetches each menu item by ID, checks availability, and snapshots the current name and price into the bill document. The bill items array stores `{ menuItemId, name, price, quantity }` rather than just the menuItemId reference.

This design protects historical data: if an admin changes a menu item's price or name after a bill is created, the bill still reflects the values at the time of sale. The totalAmount is computed on the backend by summing `menuItem.price * item.quantity`, preventing clients from manipulating the total.

The function validates that each item has a menuItemId and a positive quantity, that the referenced menu item exists and is available, and that the items array is not empty. If any validation fails, it returns 400 with a descriptive message.

## IST timezone calculation for today's bills

The getTodayBills function computes IST day boundaries by adding 5.5 hours to the current UTC time to get an IST-shifted Date object, extracting the date string, then constructing UTC midnight on that date and subtracting the offset to find the corresponding IST midnight in UTC.

```javascript
const istNow = new Date(Date.now() + istOffset);
const istDateStr = istNow.toISOString().slice(0, 10);
const startUTC = new Date(`${istDateStr}T00:00:00.000Z`).getTime() - istOffset;
const endUTC = new Date(`${istDateStr}T23:59:59.999Z`).getTime() - istOffset;
```

If the current UTC time is 2024-11-18 20:00:00, then istNow represents 2024-11-19 01:30:00 UTC (shifted forward), and istDateStr is "2024-11-19". The code computes `new Date("2024-11-19T00:00:00.000Z").getTime() - istOffset`, which is 2024-11-19 00:00:00 UTC minus 5.5 hours, giving 2024-11-18 18:30:00 UTC. This is the correct UTC timestamp for IST 2024-11-19 00:00:00, since IST = UTC + 5:30 means IST midnight is 5.5 hours after the previous day's 18:30 UTC.

## Frontend guard implementation and route protection

Both guards use Angular's functional guard pattern (CanActivateFn). The auth-guard checks for token presence, decodes the JWT by splitting on "." and base64-decoding the payload, checks the exp claim against Date.now(), and cleans up localStorage if the token is expired or malformed.

The admin-guard follows the same pattern: it checks token presence, decodes the JWT, verifies expiration, checks if payload.role === 'admin', and redirects non-admins to '/pos/billing'. Both guards return createUrlTree for redirects, which is the correct pattern for functional guards.

The routes in app.routes.ts apply guards correctly: admin routes use [authGuard, adminGuard], pos routes use [authGuard]. The guard array runs in sequence, so authGuard verifies authentication before adminGuard checks authorization.

## Component architecture and form handling

All components declare standalone: true and import their dependencies directly. Forms use ReactiveFormsModule with FormBuilder and Validators. The menu dialog validates name, category, and price (min 0). The user dialog requires username and password for new users, but only name and role for edits, using conditional validators: `this.data ? [] : [Validators.required]`.

Error handling uses MatSnackBar with `err.error?.message || 'Fallback message'`. The optional chaining handles cases where the error object doesn't have the expected structure. Loading states disable forms during submission.

## Billing screen cart and print logic

The cart is an array of `{item: MenuItem, quantity: number}`. The addToCart method checks if the item already exists using `find(c => c.item._id === item._id)` and increments quantity if present. The cartTotal getter computes the sum using reduce.

The generateBill method transforms the cart into `{items: [{menuItemId, quantity}]}`. The backend populates price and name from the menu item snapshot. The printBill method constructs receipt HTML and opens it in a new window with window.open, writes the HTML to the document, and calls window.print(). The print dialog blocks execution, keeping the window open long enough to print.

## Backend route and middleware composition

All protected routes use `router.METHOD(path, authMiddleware, [optionalAdminMiddleware], controller)`. The middleware chain runs left to right: authMiddleware verifies the JWT and attaches req.user, then adminMiddleware (if present) checks req.user.role.

The adminMiddleware does not re-verify the JWT — it trusts that authMiddleware already validated it. This is correct middleware composition. If adminMiddleware ran without authMiddleware, req.user would be undefined and the role check would fail, which is a safe failure mode.

The server.js file mounts routes at /api/auth, /api/bills, /api/menu, /api/users, and enables CORS for http://localhost:4200.

## Component-route class name matching

The app.routes.ts imports Login, Dashboard, MenuManagement, SalesReport, UserManagement, BillingScreen. The component files export classes with matching names. This is non-standard Angular naming (the convention is ComponentName + Component suffix), but it's consistent across the codebase and works correctly with standalone components.
