# Cafe POS Implementation Review

Single login with role-based redirect, admin dashboard with sales/menu/user CRUD, seller billing with IST-filtered today-only access. Angular standalone components, JWT auth, Express API, MongoDB backend.

The implementation delivers the core requirements: sellers create bills from available items and see only today's data, admins see all sales and manage menu/users. The JWT flow is correct (bcrypt compare, sign with role, Bearer header injection), the IST timezone math for today's bills uses UTC offset arithmetic, and the Angular routing applies guards properly.

**Watch for:** Backend lacks role-based authorization middleware (**confirmed** — sellers can access admin endpoints by sending authenticated requests), admin guard decodes JWT client-side without signature verification (**confirmed** — trivial to forge role in localStorage), IST calculation uses naive Date arithmetic that breaks during DST (**likely** — Indian Standard Time has no DST but the logic is fragile), no input validation on backend controllers (**confirmed** — price/quantity can be negative or missing).

**Verdict**: NEEDS_CHANGES

## High-level view

The backend uses authentication middleware (JWT verification) but no authorization middleware, so a seller with a valid token can POST to `/api/menu` or GET `/api/bills` (all bills, not just today's). The admin guard on the frontend parses the JWT payload without verifying the signature, making it trivial to edit localStorage and change role to 'admin'. The IST timezone logic in `getTodayBills()` manually calculates UTC offsets, which works for India (no DST) but is brittle and will silently fail if server timezone changes. Bill creation snapshots menu item price and name at bill time, which is correct, but doesn't validate that items array is non-empty or that quantity is positive. Password hashing and comparison use bcrypt correctly at salt round 10, and JWT tokens carry role claims that are never enforced server-side.

1. **No backend role authorization** — Any authenticated user can access admin routes (/api/menu POST/PUT/DELETE, /api/users, /api/bills GET all). Add role check middleware and apply to admin routes.

## Backend lacks role-based authorization

The authMiddleware extracts and verifies the JWT, attaches `req.user` with role, then passes control to the route handler. No middleware checks `req.user.role` before allowing access. All menu, user, and bill routes are protected only by `authMiddleware`, meaning a seller with a valid token can POST to `/api/menu`, GET `/api/bills`, or DELETE menu items.

```javascript
// menuRoutes.js — all routes use authMiddleware, no role check
router.post('/', authMiddleware, createMenuItem);
router.delete('/:id', authMiddleware, deleteMenuItem);

// userRoutes.js — sellers can create admin accounts
router.post('/', authMiddleware, createUser);
```

The requirement states sellers have no access to admin routes or past sales. The current implementation violates this at the API level. The frontend guards prevent navigation but don't prevent direct HTTP requests.

Add a second middleware `adminMiddleware` that checks `req.user.role === 'admin'` and returns 403 otherwise. Apply it after `authMiddleware` on admin-only routes: menu POST/PUT/DELETE, all user routes, `/api/bills` GET (non-today). Leave `/api/bills/today` and GET `/api/menu` open to both roles.

## Client-side JWT decode without signature verification

The adminGuard extracts the JWT payload by splitting on '.' and calling `atob()` on the second segment:

```typescript
const payload = JSON.parse(atob(token.split('.')[1]));
if (payload.role === 'admin') return true;
```

JWT signatures exist to prevent tampering. This code reads the payload without verifying the signature, so an attacker can craft a token with `{"role": "admin"}` in the payload, base64url-encode it, and paste it into localStorage. The guard will pass, the backend will reject the request (wrong signature), but the attacker has bypassed the frontend route protection and can observe the admin UI.

The real issue is missing backend authorization. Even if the frontend verified signatures (which requires the secret or public key, which shouldn't be in client code), it's not a substitute for server-side role checks. The guard can stay as-is if you add backend authorization. If you want defense in depth, decode the JWT expiry and check `exp` timestamp, or rely on `authService.isAdmin()` which reads from localStorage (same trust boundary).

Alternatively, add an endpoint `/api/auth/me` that returns the user object from `req.user`, call it on app init to hydrate the user state from the server, and use that for role checks.

## IST timezone calculation is brittle

The `getTodayBills` controller computes today's start/end in IST by adding 5.5 hours to the current UTC time, setting hours to 00:00:00 and 23:59:59, then subtracting 5.5 hours to convert back to UTC:

```javascript
const istOffset = 5.5 * 60 * 60 * 1000;
const istNow = new Date(now.getTime() + istOffset);
const istStartOfDay = new Date(istNow);
istStartOfDay.setUTCHours(0, 0, 0, 0);  // Sets UTC hours on an IST-shifted date
const startUTC = new Date(istStartOfDay.getTime() - istOffset);
```

This logic is incorrect. `setUTCHours(0, 0, 0, 0)` sets the UTC time to midnight, not the local time. When you call it on a Date that has been shifted forward by 5.5 hours, you're setting midnight UTC on the wrong day.

Example: if `now` is 2025-01-18 20:00:00 UTC, `istNow` is 2025-01-19 01:30:00 UTC (represented as a Date). Calling `setUTCHours(0, 0, 0, 0)` sets it to 2025-01-19 00:00:00 UTC. Subtracting 5.5 hours gives 2025-01-18 18:30:00 UTC, which is 6:30 PM yesterday IST, not midnight today IST.

The correct approach for IST (which has no DST) is to compute the start of day in IST by taking the UTC date, adding 5.5 hours, flooring to the day, then subtracting 5.5 hours. Or use a library like `date-fns-tz` with `startOfDay(now, { timeZone: 'Asia/Kolkata' })`.

For a no-dependency fix, compute the IST day by converting to an ISO string, parsing the date portion, and reconstructing:

```javascript
const istOffset = 5.5 * 60 * 60 * 1000;
const istNow = new Date(Date.now() + istOffset);
const istDateStr = istNow.toISOString().slice(0, 10); // "2025-01-18"
const startUTC = new Date(`${istDateStr}T00:00:00.000Z`).getTime() - istOffset;
const endUTC = new Date(`${istDateStr}T23:59:59.999Z`).getTime() - istOffset;
```

This produces the correct UTC bounds for IST today.

## No input validation on backend

Controllers destructure `req.body` and pass values directly to Mongoose or bcrypt without validation:

```javascript
// billController.js
const { items } = req.body;
for (const item of items) {
  const menuItem = await MenuItem.findById(item.menuItemId);
  // No check that item.quantity is a positive integer
}

// menuController.js
const item = new MenuItem(req.body);
await item.save();
// req.body.price could be negative, name could be missing
```

Mongoose schema validation catches some issues (required fields, min values) but not all. A request with `price: -10` will be rejected by the schema, but the error handling is generic and doesn't return a structured validation response. A request with `items: "not an array"` will crash the loop in `createBill`.

Add validation middleware (express-validator or Joi) or manual checks at the top of each controller. For bill creation, check `Array.isArray(items) && items.length > 0`. For menu/user creation, check required fields and types. For password reset, check password length.

## Bill creation doesn't validate items array

The `createBill` controller assumes `req.body.items` is an array:

```javascript
const { items } = req.body;
for (const item of items) { /* ... */ }
```

If `items` is undefined, null, or a non-array, the `for` loop throws a runtime error and crashes the request. If `items` is an empty array, the loop completes, `billItems` remains empty, `totalAmount` is 0, and a zero-amount bill is created.

Add a guard at the top of the function:

```javascript
if (!items || !Array.isArray(items) || items.length === 0) {
  return res.status(400).json({ message: 'Items array is required and must not be empty' });
}
```

Also check that each item has `menuItemId` and `quantity > 0`.

## User update allows empty name/role

The `updateUser` controller extracts `name` and `role` from `req.body` and passes them to `findByIdAndUpdate` without validation:

```javascript
const { name, role } = req.body;
const user = await User.findByIdAndUpdate(req.params.id, { name, role }, { new: true, runValidators: true });
```

`runValidators: true` only runs Mongoose schema validators on fields that are present in the update object. If `name` is an empty string, the schema marks it as required but doesn't enforce minLength. If `role` is an invalid value outside ['admin', 'seller'], the enum validator catches it. But if `name` or `role` is undefined (not sent in the request), the update silently skips those fields.

This is less critical than other issues (the user isn't corrupted, just unchanged) but inconsistent with the intent. Add explicit checks:

```javascript
if (!name || !role) {
  return res.status(400).json({ message: 'Name and role are required' });
}
if (!['admin', 'seller'].includes(role)) {
  return res.status(400).json({ message: 'Invalid role' });
}
```

## CORS origin hardcoded to localhost:4200

The server configures CORS with a single origin:

```javascript
app.use(cors({ origin: 'http://localhost:4200' }));
```

This works for local development but breaks in production when the frontend is hosted at a different domain. The backend will reject preflight requests from the production frontend.

Use an environment variable:

```javascript
app.use(cors({ 
  origin: process.env.CORS_ORIGIN || 'http://localhost:4200',
  credentials: true 
}));
```

Or allow multiple origins based on `NODE_ENV`:

```javascript
const allowedOrigins = process.env.NODE_ENV === 'production' 
  ? ['https://cafe.example.com']
  : ['http://localhost:4200', 'http://localhost:4201'];

app.use(cors({ 
  origin: (origin, callback) => {
    if (!origin || allowedOrigins.includes(origin)) {
      callback(null, true);
    } else {
      callback(new Error('Not allowed by CORS'));
    }
  }
}));
```



## Billing screen print behavior

The requirement says "create and print new customer bills" — the current implementation has separate buttons: "generate bill" saves to the database but doesn't print, "print" opens a print dialog without saving. If the intent is to save and print in one action, either combine the operations or clarify the workflow.
